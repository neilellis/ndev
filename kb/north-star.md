# Project North Star

`NORTH_STAR.md` at the repository root states what the project is for and what rules its work must follow. It can name a source that takes priority. Respect that order and the owner's rules for editing the file.

## Epic gates

- At framing, the coordinator reads the whole file before agreeing the aim or sending research briefs. Record which sections govern the epic and how the spec will test them.
- At closing, the coordinator reads the whole file again from the default branch. Use `git show <verified-revision>:NORTH_STAR.md` to read it at the revision under review. Check the merged work against the current statements. Record the sections, the evidence, and any gaps in the closing report.
- Read a long file in ranges. Give each worker the relevant section names and verification tasks in its brief.
- If the file is missing or unreadable, keep the phase open. Name the path and ask the owner to supply or restore the file. If a conflict remains, record it and ask the owner to resolve it before you finish that phase.

## Other SDLC work

Read only the sections that apply. Start with the headings if the task touches project goals, domain rules, architecture, user behaviour, or public claims. Use the named source when a section gives it priority. If the task has no bearing on those statements, proceed with the task's own checks.

Read the relevant sections before making or approving a change to the product's purpose, domain rules, or architecture across the project. Check them also in a project-wide assessment. A test or review of such a change must cite the applicable section and the behaviour it checks.

For other work, use the citations from the spec, issue, or worker brief. Check the file again if the scope changes or the evidence suggests a conflict. If the file is absent outside an epic, use the existing project guidance. Ask the owner to settle any conflict that affects the work.
